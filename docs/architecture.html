3) User Flow

A) Prospect → Member
เข้าชมหน้า public → ลงทะเบียนสนใจ (Prospect) → OTP / ยืนยันอีเมล + ยอมรับ PDPA → ทำแบบประเมิน / นัดหมาย → กรอกใบสมัคร + ส่งเอกสาร → เจ้าหน้าที่ตรวจสอบ → Admin อนุมัติ → สร้าง Member ID → BFS วางในต้นไม้ (บันทึกเหตุผล) → เปิดสิทธิ์สมาชิก → อีเมลอนุมัติ+วางตำแหน่ง
Prospect ไม่กิน Slot / ไม่สร้างรายได้จนกว่าอนุมัติ • ตรวจเบอร์/อีเมล/เอกสารซ้ำ
B) Tree Placement
ขออนุมัติ place-member {parentId} → TX + SELECT ... FOR UPDATE (parent row lock) → นับลูก parent < 5 ? วาง slot แรกว่าง → เต็ม → BFS queue ชั้นถัดไป ซ้าย→ขวา → INSERT tree_placements (unique parent+slot) → บันทึก audit + ส่งอีเมล “จัดวางแล้ว”
Strict History (default) ไม่ย้ายตำแหน่งเดิม • Vacancy Refill ต้องอนุมัติ + version ใหม่
C) Performance → Income → Payout
นำเข้า performance_records (CSV/API) → Income Rule Engine (versioned) คำนวณ → สร้าง income_transactions (Estimated) → Admin อนุมัติ → Approved → สร้าง payout_batches → Paid + เอกสาร PDF → Reversal ใช้ transaction ใหม่ ไม่ลบเดิม → อีเมลทุกสถานะ + Signed PDF link หมดอายุ

6) Placement Algorithm — ต้นไม้ฐานกว้าง 5 คน (BFS Level-Order)

กฎหลัก
  • Sponsor (คนแนะนำ) ≠ Placement Parent (ตำแหน่งในต้นไม้) — เก็บแยก
  • 1 สมาชิกมีลูกได้สูงสุด 5 ช่อง (Slot 1-5) — ห้ามเกิน
  • หา Parent แบบ BFS: ระดับตื้นสุดก่อน → ซ้ายไปขวาในระดับเดียวกัน
  • Strict History (default): ไม่ย้ายคนเดิม ไม่กิน Slot ซ้ำ
  • ใช้ Transaction + SELECT ... FOR UPDATE ล็อกแถว Parent
  • Idempotency Key กันคำสั่งซ้ำ (concurrent registration)
  • ตัวอย่าง: A มี A01-A05 → คนที่ 6 ลงใต้ A01 → A01 เต็มลง A02 ...
ตำแหน่งว่าง: แสดง “ตำแหน่งว่าง” เส้นประสีเทา • ไม่นับ Active • ไม่สร้างผลงาน/รายได้ • ห้ามสร้างชื่อสมมุติ
-- Pseudo (Postgres + Prisma) BEGIN; SELECT id FROM tree_nodes WHERE id = :requestedParent FOR UPDATE; -- 1) ลอง parent ที่ขอมาก่อน SELECT slot FROM tree_placements WHERE parent_id=:p; IF count < 5 THEN INSERT (parent_id, slot=minVacant) RETURN; -- 2) BFS หา parent ว่างใน subtree WITH RECURSIVE bfs AS ( SELECT id, 0 as depth FROM tree_nodes WHERE id=:p UNION ALL SELECT c.id, depth+1 FROM tree_nodes c JOIN tree_placements tp ON tp.child_id=c.id JOIN bfs ON bfs.id=tp.parent_id ) SELECT parent_id, slot FROM ( SELECT tp.parent_id, COUNT(*) cnt FROM tree_placements tp GROUP BY tp.parent_id HAVING COUNT(*)<5 ) q ORDER BY depth, parent_id LIMIT 1 FOR UPDATE; INSERT INTO tree_placements(parent_id, child_id, slot, reason, idempotency_key) VALUES (:foundParent, :newMember, :slot, 'BFS', :key) ON CONFLICT (idempotency_key) DO NOTHING; -- กันซ้ำ COMMIT;
กันสมาชิกซ้ำ: UNIQUE(child_id) • กัน Slot ซ้ำ: UNIQUE(parent_id,slot) • Concurrent ปลอดภัยด้วย Row Lock

8) Email Event Architecture

เหตุการณ์สำคัญ (ตัวอย่าง):
  • Prospect: ลงทะเบียน/OTP/มอบหมายที่ปรึกษา/นัดหมาย/เปลี่ยนสถานะ
  • Applicant: รับใบสมัคร/เอกสารไม่ครบ/ตรวจสอบ/อนุมัติ/สร้าง Member ID/วางต้นไม้
  • Member: อุปกรณ์ใหม่/เปลี่ยนรหัส/มีสมาชิกใหม่/ครบ 5 คน/เลื่อนตำแหน่ง/ผลงาน/รายได้/จ่ายเงิน/เอกสาร
ทุกอีเมลมี: ชื่อระบบ ชื่อผู้รับ ประเภท วันเวลา Asia/Bangkok Reference ID รายละเอียด สถานะ ขั้นตอนถัดไป ปุ่มดูรายละเอียด ช่องทางติดต่อ ข้อความปลอดภัย ลิงก์จัดการแจ้งเตือน • ห้ามส่ง รหัสผ่าน OTP หมดอายุ เลขบัตร/บัญชีเต็ม เอกสารยืนยัน รายได้คนอื่น
ป้องกันส่งซ้ำ + คิว 
email_messages { id, event_id, idempotency_key UNIQUE,
  template_version, recipient_id, status, provider_msg_id,
  attempts, error, queued_at, sent_at }

Flow: Trigger → Queue (pg-boss) → Render Template
  → Deduplicate by idempotency_key
  → Send via Resend/SES → Webhook (Delivered/Bounced/Complained)
  → Retry + Exponential Backoff → Dead Letter Queue
  → Admin: ดูประวัติ / ส่งใหม่ / Suppression List
สถานะ: Queued → Processing → Sent → Delivered / Failed / Bounced / Complained

ถัดไป: เริ่มสร้างโค้ด Production (หลังคุณอนุมัติ Architecture นี้)

ลำดับสร้าง: Scaffold → Prisma Schema → Auth/RBAC → Prospect CRM → Tree (BFS+UI) → Income+PDF → Email System → Dashboards → Tests/Seed • ทุกส่วนเชื่อม DB/Auth/RLS จริง ไม่ใช่หน้าตัวอย่าง
